# Webapp PWA conventions

Moved verbatim from `CLAUDE.md` so the always-on file stays under its size cap. `CLAUDE.md` keeps each section's heading, its *apply only if* gate and one-line rules, and points here for the full procedure, reasoning, snippets and decision records. Headings match `CLAUDE.md`'s, so a reference to a section by name resolves in either file.

## UX surface — diff-keyed design-conformance gate *(PWA)*

**Two checks, kept separate — a real gate uses both, scoped to the diff.** *Token check* (`/design-sync`-style): diffs CSS custom properties (light+dark) and the nav contract vs spec; static, no browser, never renders — catches "accent drifted", misses "nav pushed off-screen / cards overlap". *Visual verification* (`verify`-style): launches the live app, drives the touched view in a headed browser, screenshots it — the only check that *sees* the result; the token-expensive leg.

**The gate contract (shared skill behavior):**
- **Deterministic, diff-keyed — not per-run LLM judgment.** Trigger: does `git diff <main>...HEAD` intersect the declared `paths`? Yes → run; No → skip and state it in the finish summary (`no UX surface touched`). Same mechanism as `## CI expectations`'s e2e-surface skip.
- **Cheap design-aware load at `/issue-start`**: if the picked issue is likely to touch the UX surface, read `~/.claude/design.md` + `design.dark.md` before building (two file reads, no browser) — no `/design-sync`, no screenshot at start.
- **Gate at `/issue-finish` (and `/issue-yolo`), only when the diff touched the surface** — two legs:
  - **Token check, fix-now semantics.** Compare touched UX files (CSS custom properties light+dark + nav contract) to spec and fix material drift in this branch before merge — unlike vanilla `/design-sync`, which files-and-defers a `design-drift` issue for the periodic sweep.
  - **One screenshot** of the touched view via the `verify` skill, attached to the PR body. Diff-scoped, never a whole-app sweep by default.
- **Manual overrides** (mirroring `/issue-start`'s `now`/`plan`): `ux`/`design` forces the gate even if the diff looks code-only; `no-ux` skips it when the detector over-fires; `ux-full` audits the whole app's `key views` — the one expensive path, opt-in only.
- **Materiality bar** (from `/design-sync`): a 1-unit radius/spacing nitpick is not a blocker; a wrong canvas color, missing dark theme, hand-rolled nav, or visibly broken layout is.
- **Keep-the-human-in-control.** Always state the gate decision (ran/skipped/`ux-full`, plus any drift fixed) in the finish summary, so the user can veto.

**Where each piece lives:** convention + block default here; skill mechanism in `fleet-config` `skills/issue-{start,finish,yolo}/SKILL.md`; per-project instances in each project's own block; periodic fleet-wide drift sweep is separate. Browser screenshots must go through the `verify` skill's stealth-Chrome launch (real Chrome, no automation infobar, per global `CLAUDE.md`) — never re-inline launch args.

## HTTPS provisioning *(PWA)*

An installed PWA needs HTTPS (Service Workers + Web Push are HTTPS-only); which path to take depends on how the app is reached remotely.

- **Reached over Tailscale → `tailscale cert` (preferred).** Provision a real Let's Encrypt leaf for the tailnet MagicDNS name with `scripts/gen_tailscale_cert.py`. Tailscale owns `ts.net` and answers the ACME DNS-01 challenge: no public DNS name, no HTTP-01/DNS-01 setup, no inbound exposure, zero per-device trust steps. One-time prereq: enable HTTPS in the tailnet admin console (DNS → HTTPS Certificates), once per tailnet.
- **Auto-renew on startup is mandatory.** LE leaf is ~90 days (vs a self-signed root's 10 years) — manual re-issue will be forgotten. `gen_tailscale_cert.py --check` renews only a `.ts.net` cert expiring within ~30 days, no-ops a self-signed cert, never blocks startup on error. Wire `--check` into the app's own webapp launcher (e.g. `webapp.bat`), before uvicorn binds — not the generic `tray.bat.template` (cert provisioning is app-specific). Reference: `grocery-shopping-automation`'s `webapp.bat`.
- **LAN-only / no Tailscale → self-signed CA (fallback).** Keep the self-signed CA + leaf (`gen_ssl_cert.py`) and the per-device trust dance (`certutil -user -addstore Root ca.pem` + full-Chrome-restart gotcha; iOS `/install-ca` `.mobileconfig` + Certificate-Trust toggle). Correct only with no tailnet. The in-app `/install-ca` Settings affordance is scoped to this fallback — a `tailscale cert` app does not ship it.
- **Ref:** full procedure (commands, admin-console step, iPhone install): `docs/app-onboarding.md` §2–§3.

## Webapp PWA required surfaces (build-identity footer + Settings/CA-install) *(PWA)*

- **Build-identity footer — `GET /api/version` → `{git_sha, built_at}`.** Capture values once at module load via a hardened `git rev-parse --short HEAD` (`git -C <project-root>`, `stdin=subprocess.DEVNULL` + `creationflags=CREATE_NO_WINDOW`), and render `Build: <sha> · <ts>` as a plain `<p>` outside every card. A `/healthz` 200 passes on a stale process, a matching `git_sha` does not — the `/issue-finish` + `/issue-yolo` tray-restart verification depends on this endpoint existing. Auth-gated (loopback bypasses; the PWA attaches the bearer via the page's `jsonApi`) so a build SHA is never exposed to an unauthenticated remote caller. Universal — present regardless of how HTTPS is provisioned.
- **Settings block** — a collapsible `⚙️ Settings` `<details>` with an Install-certificate link to `/install-ca` (route serving the iOS `.mobileconfig`). `/install-ca` is auth-exempt, so the link is a plain `<a href>` navigation working over Tailscale without a token — not a `jsonApi` fetch. Include a short iOS trust how-to beside it. The block's app-specific contents (config fields, passkey/WebAuthn, tunnel status) are not part of the standard — only the collapsible block + CA-install affordance are.
- **The CA-install link is conditional on the HTTPS path.** Ships only on the self-signed/LAN-only fallback; a `tailscale cert` app omits or hides it. The `/api/version` footer stays regardless.
- **Ref:** the scaffold ships no starter FastAPI server, so this is documented, not seeded — a vendored `_vendored/settings/` component is a future step (`app/webapp/static/_vendored/README.md`). Reference: `app-launcher` `app/webapp/routers/misc.py` + `static/{index.html,main.js}`, and `home-automation`.

## Webapp PWA static-asset cache-busting (`CachingStaticFiles` + fleet hash) *(PWA)*

iOS Safari — installed home-screen PWAs especially — heuristic-caches static assets served by a bare Starlette `StaticFiles` mount (only `ETag`/`Last-Modified`, no explicit `Cache-Control`): after a deploy + tray restart the device runs the old cached JS/CSS while `/api/version` reports the new build. Every fleet PWA ships the same fix — a required convention, not an optional extra.

- **One canonical reference, copied — not re-derived.** `home-automation/src/static_versioning.py` plus the `CachingStaticFiles(StaticFiles)` subclass (`home-automation/app/webapp/server.py`); adapt nothing but the static dir. Canonical names: `BuildInfo.stamp_html` / `stamp_js` (wrapping `rewrite_index_html` / `rewrite_js_imports`).
- **Fleet hash, not a naive per-file hash.** The webapp is an ES-module graph (`index.html` → `main.js` → imports), so a per-file hash goes stale on transitive edits (`state.js` changes, `main.js`'s bytes don't). Use one fleet hash = a single SHA-256 over the concatenation of every hashable file's per-file hash; any edit to any module rotates every `?v=` stamp.
- **Stamp idempotently, degrade gracefully.** The import/href regexes also capture an existing `?v=…` and replace it, so re-stamping an already-served body is safe; an unreadable static dir or missing file falls back to unstamped URLs rather than crashing the page.
- **Per-suffix `Cache-Control`; the shell always revalidates.** `.js`/`.css` get `public, max-age=31536000, immutable` (safe because the fleet hash is the cache key); manifest/icons get `public, max-age=86400`. The shell (`index.html` root route) is served `Cache-Control: no-cache, must-revalidate` — otherwise a cached shell still points at the old entry module and the hashing buys nothing.
- **Ref:** reference snippet `docs/app-onboarding.md` §4. Service workers/offline caching are deliberately not used in the fleet.

## Usage log — local-only views, taps, device class *(PWA)*

Design reviews used to ask the owner "how often do you use X?" because no fleet web app recorded which views or controls were actually used, or on which device. Decision (owner, 2026-10-11): every fleet web app records usage in one shared, local-only convention, and `/design-review` consumes it as evidence, falling back to "a hypothesis the owner corrects" only for an app with no data yet.

**Privacy is the contract.** Never log message contents, document text, transcripts, names, file names, search queries, form values, URLs with query strings, IP addresses, or the raw user-agent. Only: event kind, view id, control id, a random per-visit session id, device class, and timestamps. Control ids are developer-chosen constants in `data-track`, never derived from element text or user data.

- **Two vendored halves, copied verbatim.** Client: `app/webapp/static/_vendored/usage-log/usage-log.js` (manifest key `usage-log`), dependency-free, batching `session_start` (load and each return to the foreground), `view` (`trackView(id)`, handed to the nav's `onChange(tab)` so every tab switch is a view; call it directly for a sheet or dialog), `tap` (one delegated listener; the id comes from an opt-in `data-track="<id>"` attribute, never from element text) and `session_end` (page hidden, sent with `sendBeacon`). Server: `src/usage_log.py` (manifest key `usage_log`), a FastAPI router factory mounting `POST /api/usage/events`, `GET /api/usage/summary` and `GET /api/usage/time`. Per-app variation is the `data-track` ids, the view ids and the database path, nothing else; the propagation freeze applies once adopters exist.
- **Same origin, and only that.** The client posts to a root-relative path (`/api/usage/events`); an absolute or protocol-relative endpoint disables it rather than send off-origin. No cloud analytics, no third-party service, no cross-device aggregation: each app's log stays on the machine that serves it. No session replay, heatmaps, scroll depth or per-keystroke capture.
- **Device class, never the user-agent.** The client derives `phone | tablet | desktop` (pointer type + short screen side) and `ios | android | windows | other` (a coarse user-agent match) and sends only those two words.
- **The server re-enforces the contract.** An event is stored only if its kind is in the allowlist and its id matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$` (no spaces, no `/`: a sentence, path or URL cannot pass); the envelope's session id, device class and OS class are checked too; extra keys are never read. One `events` table: `ts` (UTC, stamped on receipt), `session_id`, `kind`, `view_id`, `control_id`, `device_class`, `os_class`. Summary output counts sessions but never returns their ids.
- **Storage under the runtime-data root.** `runtime_db_path(<app>, "usage.sqlite3", create=True)` (see "Runtime data lives on a fast drive"): outside git, never committed, backed up only through the explicit runtime-data backup source like any other runtime SQLite state. Losing it loses history, not function. WAL, `synchronous=NORMAL`, one transaction per client batch (the client sends at most every 10 s, or at 50 events), never a per-tap `fsync`.
- **Retention and caps.** Every insert prunes rows older than 365 days and caps the table at 200,000 rows, oldest first; a batch holds at most 50 events and 16 KB, so a runaway client cannot fill the disk.
- **Token-gated apps pass `opts.headers`, never wrap `fetch`.** `initUsageLog({ headers })` takes an object or a per-send function (a rotating token is read fresh); with it, the page-hide send is a `keepalive` fetch because a beacon cannot carry headers. Omitted, behaviour is unchanged.
- **Instrumentation never breaks the app.** The client swallows every send failure. The endpoint answers a bad envelope with 400, an oversized body with 413, and a locked or full database with 503 plus one info-level log line; nothing raises into the UI.
- **Auth.** Both endpoints follow the app's existing rules, loopback bypass included: pass the app's auth dependency as `usage_router(..., dependencies=[Depends(require_auth)])`, or include the router where the app's auth middleware already applies.
- **Reading it for a review.** `scripts/usage_summary.py --app <slug> --days 30 --json` (in this repo) opens `<runtime-data root>/<slug>/usage.sqlite3` read-only and prints per-view visit counts, per-control tap counts, the device and OS split by session, the session count and the first/last timestamps. A missing database exits 2 with a message on stderr: "no data yet" is never reported as zero usage (an existing database with no rows in range, exit 0). `--time` prints the foreground-time report below instead.
- **Foreground time, Screen Time style.** `foreground_time(conn, since, until, tz)` computes how long the app was actually open in front of the owner, from the existing rows only: no new event kind, column or client signal, so the privacy contract is unchanged. `GET /api/usage/time?days=7&by=day|device|view` serves it for the last `days` (1–366) host-local days, today included; `by` keeps per-day totals only (`day`, the default), adds the per-device split (`device`) or the per-view split (`view`). The response carries `since`, `until`, `tz`, the `rules` constants, `total_minutes` and a `days_series` with every day in the window, zero days included, and never a session id. It reads the file read-only and never creates it: an absent file answers zeros with `"log_exists": false`, so "no data yet" stays distinct from zero usage. The seven rules, also in the module docstring:
  1. Rows are grouped by `session_id` (one page visit) and ordered by `id`, never by `ts`: the server stamps `ts` on receipt, so every event of a client batch shares one.
  2. An interval opens at `session_start`, or at the visit's first event of any kind when its start was lost, and closes at the next `session_end`.
  3. A second `session_start` before an end (a lost hide beacon) closes the open interval at the last event seen before it; a visit that never ends closes at its last event. Nothing is padded by a fixed amount, so a start-only visit (test traffic, a bounce) reads as about 0.
  4. `phone` and `tablet` intervals are trusted, because auto-lock hides the page; they are cut only at `MAX_INTERVAL` (4 h) as a lost-end safety net. On `desktop`, where a visible tab never reports hidden, a stretch longer than `IDLE_GAP_DESKTOP` (15 min) with no event in it counts as 15 min. Both are overridable keyword arguments.
  5. Time is split at local midnight in the caller's `tz` (`None` = the host's local time, with its own DST rules); the day is the local date.
  6. A day's total is the union of all intervals, so two tabs, or a phone and a PC at once, are never counted twice. Each device class is the union of its own intervals, so device rows may sum to more than the total. Each slice goes to the visit's latest `view` at that moment (`(none)` before its first one), and where visits overlap, to the most recently started interval, so view rows sum to the total.
  7. Accepted error: a start is stamped up to one client flush (10 s) late, so a visit shorter than that reads as 0. This small, systematic undercount is documented, not corrected. A desktop heartbeat or focus signal would be new recorded data and needs its own issue.
- **Ref:** markup contract, event schema and wiring snippet: `app/webapp/static/_vendored/usage-log/README.md`. Proof: `tests/test_usage_log.py` (validation, retention, privacy, router, CLI, foreground time) and `tests/e2e/test_vendored_usage_log.py` (the gallery's view switch and tracked tap read back through the summary, every request same-origin).
